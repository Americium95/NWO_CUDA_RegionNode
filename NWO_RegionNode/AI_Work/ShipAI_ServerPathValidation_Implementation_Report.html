NWO RegionNode 서버 0x06/0x00 경로검증 구현 보고서

대상 프로젝트: NWO_RegionNode (net6.0, DotNetty 0.7.2, TCP 19100)
대상 파일: NWO_RegionNode/ 아래 서버 측 구현 일체
문서 상태: 독립 리뷰 지적사항(프레이밍 부재, 방문점 순서 검증 취약, provider 비연동, 버퍼 소유권, 샘플링 방식, 보고서 미비)을 반영해 수정한 최종 구현 기준

현재 판정 요약: 0x06/0x00 요청은 파싱·거부 응답까지 동작하지만, 정답을 인정(Accepted)하는 경로는 아직 존재하지 않습니다. 권위 있는 NavMesh provider가 실제로 구성되지 않은 동안에는 모든 플랜이 거부(fail-closed)됩니다. 신뢰 구간(신뢰 경로 섹션)은 표본으로 추출되며 전체 경로 인접성을 결정론적으로 순회하지 않는다. 기본 표본 예산은 min(64, 세그먼트 수)개의 고유 에지이며, 표본에 포함되지 않은 세그먼트에는 확률적 갭/재시도 리스크가 존재한다. 3절과 8절을 반드시 함께 읽으십시오.

1. 처리 흐름 요약

기존 서버는 프레임 디코더가 없는 raw TCP 핸들러(EchoServerHandler)였고, TCP read 1회 = 패킷 1개라는 암묵 가정에 의존했습니다. 새 요청 0x06/0x00은 헤더에 totalPacketLength를 광고하므로, 이 가정 위에서는 split/coalesced read가 곧바로 파싱 오류를 유발합니다. 이를 해결하기 위해 0x06에 한정해 스트림 누적/프레이밍 핸들러 (PathFrameDecoder)를 실제 부트스트랩 파이프라인에 삽입했습니다. 레거시 0x02/0x04 패킷은 원본 버퍼를 그대로 후행 핸들러로 전달되므로 처리 방식이 바뀌지 않습니다. 단, 한 read 안에 레거시 패킷과 0x06 프레임이 섞여 들어온 경우에는 프레임 경계를 알 수 없으므로 해당 채널만 종료합니다(3.4절). 기존처럼 통째로 전달하면 뒤따른 0x06 요청이 조용히 유실되기 때문입니다. 

pipeline.AddLast("pathframe", new PathFrameDecoder());   // 0x06 한정 누적/프레이밍
pipeline.AddLast("echo",     new EchoServerHandler(pathProvider)); // 레거시 + 0x06 검증

3. 스트림 프레이밍 (PathFrameDecoder.cs)

3.1 왜 필요한가

DotNetty 소켓 파이프라인은 read 경계를 보존하지 않습니다. 한 번의 ChannelRead에 0x06 프레임이 절반만 도착하거나, 프레임 2개 + 레거시 패킷이 함께 도착할 수 있습니다. 기존 EchoServerHandler는 buffer.GetByte(0..N)으로 한 패킷을 통째로 가정하므로, 0x06에 대해 이 가정을 그대로 쓰면 조각난 프레임을 잘못 해석하거나 예외로 채널이 닫혔습니다.

3.2 처리 규칙

조건동작레거시 영향
메시지가 IByteBuffer가 아님 또는 ReadableBytes ≤ 0즉시 해제 후 폐기없음 (기존에도 무시)
진행 중인 0x06 프레임이 있음(_pendingCount > 0)다음 바이트를 무조건 누적 배열에 추가(프레임이 선언된 길이를 채울 때까지)레거시 바이트가 프레임 시작 위치에 도달하면 아래 "인터리빙" 행에서 채널 종료. 유효 헤더 뒤에 도달하면 payload로 간주되어 누적됨(3.4절 참조)
누적 중 프레임 시작 위치의 바이트가 0x06이 아님(레거시 인터리빙)로그 후 해당 채널 종료(fail-closed)레거시 패킷은 처리되지 않고 채널이 닫힘 — 프레임 유실 대신 확정적 실패
첫 바이트가 0x06읽기 가능한 바이트를 누적 배열에 복사 후 입력 버퍼를 1회 해제0x02/0x04 패킷은 첫 바이트가 0x02/0x04이므로 절대 누적 대상이 되지 않음
누적 바이트 첫 바이트가 0x06이고 선언 길이까지 모였음프레임을 잘라 후행 전달하고, 남은 꼬리(레거시 포함)를 다음 반복에서 계속 처리프레임 뒤 레거시 꼬리는 지연 없이 전달됨(복사 1회 추가)
첫 바이트가 0x06이 아니고, 버퍼 어딘가에 완전한 0x06/0x00 헤더(8바이트, 유효 길이)가 있음로그 후 해당 채널 종료(fail-closed) — legacy-first coalesced 거부레거시 패킷도 처리되지 않고 채널이 닫힘 — 0x06 요청의 조용한 유실 방지
첫 바이트가 0x06이 아니고, 완전한 0x06 헤더가 없음원본 버퍼를 그대로 후행 핸들러로 전달(소유권 이전, 복사 없음)없음 — 기존과 바이트 단위로 동일
0x06 이지만 subtype ≠ 0x00로그 후 해당 채널 종료(fail-closed)없음 (레거시 opcode는 0x02/0x04)
length 필드가 12 미만이거나 1,048,576 초과로그 후 해당 채널 종료(fail-closed)없음 (동일)
누적 바이트 > 1,048,576로그 후 해당 채널 종료없음 (동일)
선언 길이보다 누적 바이트가 적음다음 read를 기다림(break 후 컴팩트)해당 채널의 부분 프레임만 보류

위 표의 "완전한 0x06/0x00 헤더" 판정은 ContainsPathFrameHeader가 수행합니다. 레거시 시작 read에서 opcode 0x06 + subtype 0x00 + totalPacketLength ∈ [12, 1048576]인 8바이트 패턴을 찾으면 혼합으로 간주합니다. 헤더가 8바이트 미만으로만 존재하는 경우는 길이 필드를 신뢰할 수 없어 레거시로 원본 전달(기존 동작 유지)을 선택합니다.

public override void ChannelRead(IChannelHandlerContext context, object message)
{
    var buffer = message as IByteBuffer;
    if (buffer == null || buffer.ReadableBytes <= 0)
    {
        ReferenceCountUtil.SafeRelease(message);
        return;
    }

    // A 0x06 frame is already in flight. Every following byte belongs to that
    // frame until the advertised length is satisfied, so it is accumulated
    // unconditionally. Any non-0x06 byte seen by Drain is an unsupported
    // interleave and terminates the channel (see Drain).
    if (_pendingCount > 0)
    {
        Append(buffer);
        ReferenceCountUtil.SafeRelease(buffer);

        if (_pendingCount > MAX_FRAME_LENGTH)
        {
            Console.WriteLine("[path] 0x06 accumulation overflow, channel closed");
            _pendingCount = 0;
            context.CloseAsync();
            return;
        }

        Drain(context);
        return;
    }

    // No frame in flight. A read that starts with 0x06 begins a 0x06 stream.
    if (buffer.GetByte(buffer.ReaderIndex) == PATH_OPCODE)
    {
        Append(buffer);
        ReferenceCountUtil.SafeRelease(buffer);

        if (_pendingCount > MAX_FRAME_LENGTH)
        {
            Console.WriteLine("[path] 0x06 accumulation overflow, channel closed");
            _pendingCount = 0;
            context.CloseAsync();
            return;
        }

        Drain(context);
        return;
    }

    // The read starts with a legacy 0x02/0x04 packet. Legacy packets carry no
    // length field, so this decoder cannot tell where that packet ends and
    // therefore cannot split a trailing coalesced 0x06 frame off it without
    // risking an offset misread of the legacy payload.
    //
    // Rather than forwarding the whole buffer and silently discarding the
    // trailing 0x06 request, an unframeable mix is rejected deterministically:
    // the channel is closed so nothing is lost quietly.
    if (ContainsPathFrameHeader(buffer))
    {
        Console.WriteLine("[path] legacy packet coalesced with 0x06 frame, channel closed");
        ReferenceCountUtil.SafeRelease(buffer);
        context.CloseAsync();
        return;
    }

    // Pure legacy read: forward the original buffer untouched.
    context.FireChannelRead(buffer);
}

private void Drain(IChannelHandlerContext context)
{
    int offset = 0;
    while (_pendingCount - offset > 0)
    {
        // A 0x06 frame was declared in flight but this byte is not 0x06:
        // legacy bytes were interleaved into the middle of a frame. The
        // declared length can no longer be trusted, so no safe split exists.
        // Fail closed instead of guessing and losing a frame.
        if (_pending[offset] != PATH_OPCODE)
        {
            Console.WriteLine("[path] legacy bytes interleaved into 0x06 frame, channel closed");
            _pendingCount = 0;
            context.CloseAsync();
            return;
        }

        if (_pendingCount - offset < 2)
        {
            break;
        }

        if (_pending[offset + 1] != PATH_REQUEST_SUBTYPE)
        {
            Console.WriteLine("[path] unsupported 0x06 subtype, channel closed");
            _pendingCount = 0;
            context.CloseAsync();
            return;
        }

        if (_pendingCount - offset < LENGTH_FIELD_END)
        {
            break;
        }

        uint total = ReadLength(_pending, offset);
        if (total < MIN_FRAME_LENGTH || total > MAX_FRAME_LENGTH)
        {
            Console.WriteLine($"[path] invalid 0x06 frame length {total}, channel closed");
            _pendingCount = 0;
            context.CloseAsync();
            return;
        }

        if (_pendingCount - offset < (int)total)
        {
            break;
        }

        var frame = new byte[total];
        Buffer.BlockCopy(_pending, offset, frame, 0, (int)total);
        offset += (int)total;
        context.FireChannelRead(Unpooled.CopiedBuffer(frame));
    }

    Compact(offset);
}

private static bool ContainsPathFrameHeader(IByteBuffer buffer)
{
    int start = buffer.ReaderIndex;
    int readable = buffer.ReadableBytes;
    for (int i = 0; i + LENGTH_FIELD_END <= readable; i++)
    {
        int pos = start + i;
        if (buffer.GetByte(pos) != PATH_OPCODE
            || buffer.GetByte(pos + 1) != PATH_REQUEST_SUBTYPE)
        {
            continue;
        }

        uint total = (uint)(buffer.GetByte(pos + 4)
            | (buffer.GetByte(pos + 5) << 8)
            | (buffer.GetByte(pos + 6) << 16)
            | (buffer.GetByte(pos + 7) << 24));

        if (total >= MIN_FRAME_LENGTH && total <= MAX_FRAME_LENGTH)
        {
            return true;
        }
    }

    return false;
}

3.4 설계 상 정확히 지원되는 범위 / 지원하지 않는 범위

지원 (0x06 한정)
· 0x06/0x00 프레임이 여러 TCP read에 걸쳐 나누어 도착하는 경우 — 길이 필드가 광고한 L 바이트가 모일 때까지 누적 후 처리.
· 0x06/0x00 프레임 여러 개가 한 read에 함께 도착하는 경우 — 루프가 순서대로 잘라 각각 검증·응답.
· 0x06/0x00 프레임 뒤에 레거시 패킷이 같은 read에 이어지는 경우 — 프레임을 꺼낸 뒤 꼬리를 즉시 후행 전달.
지원하지 않음 — 의도적으로 채널 종료(fail-closed)하여 거부
아래 두 혼합 시퀀스는 레거시 패킷에 길이 필드가 없어 프레임 경계를 알 수 없으므로 안전하게 분리할 수 없습니다. 이전 구현처럼 통째로 레거시로 전달하면 뒤따른 0x06 요청이 조용히 유실되므로, 대신 해당 채널만 즉시 종료하여 어떤 프레임도 조용히 버려지지 않게 하는 쪽을 택했습니다.
혼합 시퀀스판정사유
레거시 0x02/0x04 패킷 뒤에 완전한 0x06/0x00 프레임이 같은 read에 이어짐 (legacy-first coalesced) 채널 종료
[path] legacy packet coalesced with 0x06 frame, channel closed		 레거시 패킷에 길이 필드가 없어 어디서 0x06 프레임이 시작되는지 확정할 수 없습니다. 길이를 신뢰하고 잘라내면 레거시 페이로드를 오프셋 오독합니다.
부분 0x06 프레임 진행 중 동일 채널로 레거시 바이트가 인터리빙 — 프레임 시작 위치에 도달한 경우 채널 종료
[path] legacy bytes interleaved into 0x06 frame, channel closed		 프레임이 이미 시작된 뒤 길이 필드 경계가 무너집니다. 재동기화하면 0x06 프레임 또는 레거시 패킷 중 하나를 반드시 잃습니다.
부분 0x06 프레임 진행 중 레거시 바이트가 완전한 유효 헤더 뒤(프레임 payload 내부)에 도달한 경우 프레이밍 계층에서 감지 불가 — 바이트를 프레임 payload로 간주해 누적 헤더가 이미 통과한 뒤에는 남은 L 바이트가 "프레임 payload"인지 "레거시 패킷"인지 바이트 값만으로 구별할 수 없습니다. 이 경우 Drain의 루프가 종료되지 않으므로 채널은 열려 있으나 오염된 프레임이 PathPacketHandler의 필드 검증에서 거부(Rejected)됩니다. 클라이언트가 0x06 프레임 도중 레거시 패킷을 끼워 넣으면 응답이 오지 않으므로, 규약상 0x06 프레임은 연속으로만 송신해야 합니다.
레거시 read 안에 0x06/0x00 + 유효 길이 헤더가 존재 (헤더 8바이트 완비) 채널 종료 (위 1행과 동일) 레거시 시작 read에 0x06 헤더가 보이면 혼합으로 간주합니다. 레거시 payload의 임의 바이트가 우연히 0x06/0x00 패턴을 만들 확률은 극히 낮습니다.
레거시 read 끝에 0x06 헤더가 8바이트 미만으로만 존재 레거시로 원본 전달 (기존 동작 유지) 길이 필드가 불완전해 경계를 확정할 수 없고, 단독 0x06 바이트는 정상 레거시 payload에도 나타날 수 있어 오탐 비용이 큽니다. 이 드문 경계는 기존 레거시 의미론을 우선했습니다.
길이 필드가 손상된 0x06 스트림 (범위 밖) 채널 종료 (재동기화 없음) 프레임 경계를 신뢰할 수 없는 상태에서 재동기화하면 레거시 패킷을 오프셋 오독하므로 확정적인 실패를 택했습니다.
레거시 의미론 보존: 0x06 헤더가 전혀 없는 순수 레거시 read는 원본 버퍼를 그대로 후행 전달합니다(복사 없음, 바이트 단위 동일). 레거시 패킷 자체의 split/coalesced 대응은 여전히 범위 밖이며, 한 read에 레거시 패킷 2개가 오면 첫 패킷만 처리되고 나머지는 버려집니다(기존 동작 그대로).

6. 방문점(visit) 검증

리뷰 지적 "visit가 통로에 존재하는지 확인하지 않음 / order만 비교"을 반영했습니다. 이제 (a) order 값이 0부터 연속된 방문 인덱스와 정확히 같아야 하고, (b) 각 방문 폴리곤이 provider에 존재하며, (c) 방문점들이 제출된 통로 위에서 order 순서의 단조 증가 부분수열이어야 합니다. 커서는 앞으로만 전진하므로 O(경로길이 + 방문수)이고, 통로에 존재하지 않거나 뒤로 되돌아가야만 가능한 방문은 거부됩니다. 

private bool ValidateVisits(List<VisitEntry> visits, int[] path, PathValidationResult res)
{
    int cursor = 0;
    for (int i = 0; i < visits.Count; i++)
    {
        VisitEntry v = visits[i];
        if (v.Order != i)
        {
            res.Decision = (byte)PathDecision.Rejected;
            res.ReasonCode = (ushort)PathReasonCode.VISIT_ORDER_MISMATCH;
            return false;
        }

        if (!_provider.HasPolygon(v.PolygonIndex))
        {
            res.Decision = (byte)PathDecision.Rejected;
            res.ReasonCode = (ushort)PathReasonCode.VISIT_UNREACHED;
            return false;
        }

        bool reached = false;
        while (cursor < path.Length)
        {
            if (path[cursor] == v.PolygonIndex)
            {
                cursor++;
                reached = true;
                break;
            }
            cursor++;
        }

        if (!reached)
        {
            res.Decision = (byte)PathDecision.Rejected;
            res.ReasonCode = (ushort)PathReasonCode.VISIT_ORDER_MISMATCH;
            return false;
        }
    }
    return true;
}

7. 기하 샘플링

리뷰 지적 "중복 샘플링 가능 + 비암호화 난수"를 반영했습니다. System.Random을 버리고 RandomNumberGenerator.GetInt32(CSPRNG)를 직접 사용하며, 부분 Fisher–Yates 셔플로 중복 없이 최대 64개 구간을 선택합니다. 구간 수가 64개보다 적으면 min(64, 구간수)개를 전부 검사합니다. 인접성(CanMoveBetween)과 기하(ValidateGeometry) 검사는 각 표본 세그먼트에 대해 한 루프에서 함께 수행되며, 전체 경로를 결정론적으로 순회하지 않습니다. 신뢰 구간(신뢰 경로 섹션)은 표본으로 추출되며, 표본에 포함되지 않은 세그먼트에는 확률적 갭/재시도 리스크가 존재합니다. 어떤 프로브 하나라도 실패하면 즉시 fail-closed로 거부하며, provider가 false를 반환하면서 사유를 VALID로 준(이상한) 경우에도 FORBIDDEN_REGION으로 정규화해 거절합니다. 

private bool ProbeSampledSegments(int[] path, int sampleCount, out PathReasonCode reason)
{
    reason = PathReasonCode.VALID;

    int segmentCount = path.Length - 1;
    var order = new int[segmentCount];
    for (int i = 0; i < segmentCount; i++)
    {
        order[i] = i;
    }

    for (int i = 0; i < sampleCount; i++)
    {
        int j = i + RandomNumberGenerator.GetInt32(segmentCount - i);
        int swap = order[i];
        order[i] = order[j];
        order[j] = swap;
    }

    for (int i = 0; i < sampleCount; i++)
    {
        int segment = order[i];
        int from = path[segment];
        int to = path[segment + 1];
        if (!_provider.CanMoveBetween(from, to))
        {
            reason = PathReasonCode.PATH_DISCONTINUITY;
            return false;
        }
        if (!_provider.ValidateGeometry(new int[] { from, to }, out _, out _, out PathReasonCode providerReason))
        {
            reason = providerReason == PathReasonCode.VALID
                ? PathReasonCode.FORBIDDEN_REGION
                : providerReason;
            return false;
        }
    }

    return true;
}
