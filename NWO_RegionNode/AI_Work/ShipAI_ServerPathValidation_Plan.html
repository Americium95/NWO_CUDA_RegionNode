1. 프로젝트 구조와 현재 통신 방식

현재 프로젝트는 .NET 6 콘솔 서버이며 Program.Main → RunServerAsync → DotNetty TCP :19100 → EchoServerHandler.ChannelRead 구조다. Program.cs의 19100 파이프라인에는 pipeline.AddLast("echo", new EchoServerHandler()) 한 줄만 있고 길이 프레이밍 decoder가 없다. 기존 패킷은 첫 바이트가 opcode(buffer.GetByte(0)), 두 번째 바이트가 서브 타입이며 payload는 BitConverter 기반 little-endian 바이너리다. 0x02 계열은 사용자 위치 동기화, 0x04 계열은 오브젝트 상태/공격이다. 경로 계획 검증은 기존 0x04 계열의 미할당 서브타입으로 확장하여 처리한다(요청 0x10, 응답 0x11). 0x10/0x11은 현재 소스 검색 기준 미할당으로 간주한다.

Program.cs

TCP 서버 bind(:19100), 주기 동기화 및 브로드캐스트. 프레이밍 decoder 없음.

EchoServerHandler.cs

opcode(0)/서브타입(1) 디스패치, 고정 오프셋 읽기, 상태 갱신

Terrain.cs

현재 지형 높이 샘플 기반 충돌 보조 로직. navmesh가 아니다.

AI_Work/

이 문서와 구현 차이안·경로 프로토콜 산출물 위치

기존 핸들러는 ChannelHandlerAdapter를 직접 상속해 수신 IByteBuffer를 해제하지 않고 readerIndex도 전진시키지 않은 채 GetByte(0..) 절대 오프셋만 읽는다. 즉 기존 프로토콜에는 길이 프리픽스도, 고정 길이 검증도, 소비 규칙도 없다. 본 설계는 기존 TCP 서버(포트 19100)에 공유되는 확장으로, 패킷은 자기 헤더에 전체 길이를 담는 자기 경계(self-delimiting) 형식의 12바이트 헤더([opcode 0x04:1][subtype request 0x10/response 0x11:1][protocolVersion uint16:1][totalPacketLength uint32:4][requestId uint32:4], LE)를 유지한다. 같은 TCP 스트림에서 기존 0x02/0x04 패킷과 새 0x04/0x10, 0x04/0x11 패킷을 섞어 처리하려면, 프레이밍/디스패치 계층이 스트림 앞단에서 opcode/subtype를 먼저 검사하여 각 메시지의 헤더/길이 규칙에 따라 정확히 소비해야 하며, 기존 핸들러 자체는 현재 이 스트림 프레이밍 규칙을 따르지 않으므로 기존 고정길이 라우팅은 분리/재검토가 필요하다.

현재 프로젝트에는 navmesh와 경로 검증이 구현되어 있지 않으므로 아래 규약은 추가 구현 제안이며 아직 어떤 서버 소스에도 적용되지 않았다.

2. 목표와 신뢰 경계

클라이언트 책임

현재 선박 상태, 목적지 다각형, 방문 계획과 자신이 계산한 다각형 통로(polygon corridor)를 제출한다.

서버 책임

서버가 보유한 navmesh와 규칙으로 요청을 정규화하고, 통로 전체 구조와 무작위 구간을 서버 기하로 재계산해 검증한다.

판정 원칙

클라이언트가 보낸 polygonIndex, visitId, 순서, 길이 성질은 증거가 아니라 주장(claim)이다. 최종 판정은 서버 계산으로만 내린다.

무작위 구간 표본검사는 위험 기반 완화다. 검사하지 않은 구간까지 수학적으로 보증하지 않는다. 신뢰 구간(신뢰 경로 섹션)은 표본으로 추출되며, 전체 경로의 인접성을 결정론적으로 모두 순회하지 않는다. 기본 표본 예산은 min(64, 세그먼트 수)개의 고유 에지이며, 표본에 포함되지 않은 세그먼트에는 확률적 갭이 존재한다. 보상·경쟁 등 고위험 행동에는 전체 통로 검증 또는 표본 수 상향 정책을 적용한다.

2.1 polygon index의 의미 조건 (핵심)

정수 polygonIndex는 좌표가 아니며 전역 식별자가 아니다. 서버 navmesh의 다각형 배열 순번일 뿐이며, 그 배열은 navMeshVersion이 지정한 특정 버전에서만 유효하다. 따라서 규약은 다음을 강제한다.

  • 버전 선행 검사: 서버는 요청 navMeshVersion이 서버 권위 버전과 바이트 단위로 일치하는지 다각형 인덱스를 하나라도 해석하기 전에 확인한다. 불일치 시 resync_required로 즉시 종료하고 어떤 인덱스도 해석·비교·조회하지 않는다.
  • 같은 버전 안에서만 통상: 일치한다고 해도 인덱스의 존재·범위·인접성은 서버 navmesh 테이블에서 다시 조회한다. 클라이언트가 보낸 번호가 서버 테이블에 없으면 거절이다.
  • 버전이 바뀌면 인덱스 재사용 불가: 클라이언트 navmesh 애셋이 갱신되면 이전 인덱스로 만든 통로는 의미가 사라진다. 서버 navmesh 배포와 클라이언트 애셋 배포는 반드시 navMeshVersion으로 동결되어야 한다.
  • 버전 불일치 응답의 인덱스: resync_required 응답에는 요청 인덱스를 해석해 얻은 어떤 값도 담지 않는다. 오직 서버 권위 버전 문자열만 돌려준다.

3. 요청 흐름

인증 세션→헤더·길이·버전 검사→본문 바인딩/범위/오버플로 검사→navMeshVersion 일치→통로 구조·인접성 검증→서버 무작위 포털 표본 생성→서버 navmesh 기하 probe→수락·거절·제한

표본은 요청 안에 클라이언트 seed가 없다. 서버 CSPRNG로 뽑고, 재현 가능한 감사가 필요하면 서버 secret과 요청 식별자를 이용한 HMAC 기반 선택을 서버 로그에 저장한다. 응답에 표본 인덱스·표본 좌표·난수 seed를 절대 담지 않는다.

4. 경로 송수신 인터페이스 규약 (바이너리)

실제 송수신은 DotNetty TCP 위에 바이너리 와이어 포맷만 사용한다. 본문은 텍스트/JSON/REST/HTTP가 아니다. REST/HTTP는 사용하지 않는다. 모든 정수 필드는 little-endian, 고정 폭이며, 문자열은 UTF-8 바이트 + 선행 바이트 길이(NUL 종단 없음)다.

4.1 전송 프레이밍과 기존 opcode 호환성

0x04/0x10·0x04/0x11 경로 프로토콜 패킷은 헤더 안에 전체 길이(totalPacketLength)를 갖는다. 즉 길이 프리픽스를 별도로 붙이지 않으며, 패킷 자체가 경계를 정의한다(자기 경계).

[클라이언트]                                  [서버 · 기존 19100 공유 연결의 프레이머]
  04 10 헤더(12B) + 본문  ──────▶   바이트 누적 버퍼
                                          1) 1바이트 모였는가?            (opcode peek)
                                          2) 2바이트 모였는가?            (subtype peek)
                                          3) opcode==0x04 and subtype ∈ {0x10, 0x11} 인가?
                                               아니면 → 기존 0x02/0x04 고정길이 규칙으로 위임
                                          4) 12바이트 모였는가?  (opcode·subtype·version·totalPacketLength·requestId)
                                          5) 12 <= totalPacketLength <= 1,048,576 ?  protocolVersion==1 인가?
                                          6) totalPacketLength 바이트 모였는가?

byte[0] == 0x04 and byte[1] == 0x11PathPlan 응답(0x04/0x11) — 경로 프로토콜로 프레이밍해 정확히 소비한 뒤, 서버 포트는 요청만 수신하므로 방향 위반으로 fail-closed(연결 종료)응답을 요청으로 해석, 기존 고정길이 해석 혼동
byte[0] == 0x02 또는 (byte[0] == 0x04 and byte[1] not in {0x10,0x11})기존 0x02/0x04(기타 서브타입) 경로의 고정 길이 규칙으로 그대로 위임길이 프리픽스 해석
byte[0]가 그 외알 수 없는 프로토콜로 간주하고 연결 종료(fail-closed)1바이트 건너뛰고 재탐색(패킷 중간에서 동기화됨)

기존 0x02/0x04와의 호환성 — 결론. 새 경로는 opcode 0x04, subtype 0x10(요청)/0x11(응답)로 기존 0x04 계열과 같은 opcode 안에서 분기된다. 따라서 opcode 한 바이트만으로는 두 경로를 가를 수 없고, 디스패치는 (opcode, subtype) 두 바이트를 peeking(인덱스 미전진)하여 판별해야 한다. 0x04/0x10·0x04/0x11은 totalPacketLength로 자기경계를 정의하고, 0x02 및 0x04의 그 밖 서브타입은 기존 고정 길이 테이블로 경계를 잡는다. 같은 TCP 연결(기존 공유 포트 19100)에서 섞어 읽기 위해서는 스트림 프레이밍 계층이 (opcode, subtype) 기반으로 정확히 메시지 단위로 소비해야 한다. 기존 EchoServerHandler는 readerIndex를 전진시키지 않고 첫 바이트 절대 오프셋만 읽으며 수신 IByteBuffer를 해제하지도 FireChannelRead하지도 않으므로, (opcode, subtype)를 먼저 검사하는 프레이머/디스패처를 스트림 앞단에 배치하여 각 경로로 위임하고, 기존 핸들러가 보는 바이트 스트림이 올바르게 소비되도록 소비 규칙(consume)을 명확히 해야 한다. 본 설계는 기존 프로토콜 레이아웃은 변경하지 않는다는 원칙 하에 확장만을 제안하며, 별도 포트/별도 리스너를 추가하지 않는다.

기존 패킷의 고정 길이는 소스에서 읽는 최대 오프셋으로 얻는다(현 코드가 검증하지 않으므로 “필요 최소 길이”다): 0x02/0x00=6, 0x02/0x01=25, 0x02/0x02=12, 0x04/0x00=19, 0x04/0x01=21, 0x04/0x02=11, 0x04/0x03=2, 0x04/0x04=28. 테이블에 없는 (opcode, 서브타입) 조합은 길이를 추측하지 않고 연결을 종료한다.

4.2 공통 헤더 — 정확히 12 바이트

오프셋  크기  타입      필드                  값/설명
  0      1    byte      opcode                0x04 (기존 0x04 계열 확장)
  1      1    byte      subtype               요청 0x10, 응답 0x11
  2      2    uint16    protocolVersion       1 (LE)
  4      4    uint32    totalPacketLength     LE. 헤더 12바이트를 포함한 전체 패킷 길이
  8      4    uint32    requestId             LE. 요청-응답 상관관계 (서버 검증 로직은 사용하지 않음)

헤더 크기 = 1+1+2+4+4 = 12 bytes  (고정)
본문 시작 = 패킷 오프셋 12, 본문 길이 = totalPacketLength - 12
요청 바이트 시작: 04 10 01 00 | LLLLLLLL | RRRRRRRR
응답 바이트 시작: 04 11 01 00 | LLLLLLLL | RRRRRRRR
  • totalPacketLength는 헤더를 포함한 값이므로 bodyLength 필드를 따로 두지 않는다. 본문 길이는 항상 totalPacketLength - 12로 유일하게 결정된다(별도 bodyLength 필드가 없으므로 불일치 가능성 자체가 없다).
  • 프레이밍 검증이 통과하면 본문은 반드시 정확히 totalPacketLength - 12 바이트여야 한다. 남거나 모자라면 잘라내지 않고 거절한다.
  • requestId는 전송 계층의 상관관계용이다. 검증 로직은 planSequence로만 요청/응답을 대조한다.
  • 응답 requestId는 요청 값을 그대로 복사한다. 서버는 requestId가 0이어도 planSequence나 사유 코드로 원인을 특정할 수 없으므로 클라이언트 로그는 (opcode, subtype, requestId, totalPacketLength)만 남긴다.

경로(polygon corridor) 규칙

  • pathPolygonIndex는 전체 순서 있는 다각형 통로다. 부분 경로나 생략이 아니라 모든 통과 다각형을 순서대로 담는다.
  • 시작 인덱스(path[0])는 startPolygonIndex와 같아야 하고, 마지막(path[P-1])는 destinationPolygonIndex와 같아야 한다.
  • 연속 중복 인덱스는 클라이언트가 압축해서 보낸다. 인접 두 원소가 같은 polygon id이면 전송 전에 하나로 합치고, pathPolygonCount는 압축 후 길이여야 한다. 서버는 압축되지 않은 입력을 PLAN_INVALID로 거절한다(같은 다각형 안에서의 왕복 이동은 통로가 아니라 노이즈이며 표본 예산을 소모한다).
  • 압축 후 길이가 [2, 4096]을 벗어나면 거절한다. pathPolygonCount가 4096 초과면 서버는 배열을 할당하지 않고 즉시 거절한다.
  • 인접 두 다각형의 인접성(공유 포털 존재 여부)은 클라이언트가 보장하는 것이 아니다. 서버가 자기 navmesh에서 조회·검증한다. 비인접이면 PATH_DISCONTINUITY다.
  • 경로에 위경도·높이·거리 등 기하 좌표를 담지 않는다. 기하는 서버 navmesh가 소유하며, 클라이언트가 보낸 숫자는 전부 검증 대상 "주장"이다.

1 MiB 상한과 필드별 상한은 역할이 다르다. 1 MiB은 전송 계층의 메모리 방어선(파싱 전 검사)이고, 필드별 상한은 v1 계약이다. 규약을 지킨 클라이언트가 만드는 패킷은 최악에도 34,988바이트로 1 MiB의 약 3.3%다. 34,988을 넘는 요청은 제약을 위반한 요청이므로 즉시 INVALID_REQUEST로 거절한다(길이를 신뢰하고 버퍼를 잡아서는 안 된다).

9 · 무작위 기하 검사서버 navmesh 기준으로 선택된 스텝의 공유 포털 내부와 다각형 내부를 일정 간격 샘플링. 각 샘플이 통행 가능 분류이고 폭(clearance)이 선박 빔+여유 이상인지 검사OFF_MESH_SAMPLE / FORBIDDEN_REGION

단계 7은 이 규약의 구조적 핵심이다. 인접성 검사가 없으면 클라이언트는 "다각형 5 → 다각형 900"처럼 임의 점프를 넣어 육지를 가로지르는 통로를 지날 수 있고, 서버 무작위 probe는 그중 검사하지 않은 스텝을 그대로 통과한다. 인접 검사와 기하 검사는 서버 CSPRNG로 선택된 최대 64개 고유 세그먼트에 대해 한 루프에서 함께 수행되며, 전체 스텝을 결정론적으로 모두 순회하지 않는다. 표본에 포함되지 않은 세그먼트에는 확률적 갭/재시도 리스크가 존재하며, 이는 클라이언트 재요청(새 표본 추출)로 완화한다.

단계 9의 샘플은 클라이언트 좌표가 아니라 서버 navmesh 좌표에서 계산된다. 표본 지점은 서버 CSPRNG가 고르며 응답에 노출되지 않는다.

6. 무작위 표본 정책

  • 표본 단위는 통로 스텝(인접 다각형 한 쌍)이다. 가중치는 클라이언트가 아니라 서버가 계산한 다각형 중심 간 거리(길이 균등 밴드)로 주어, 긴 스텝에 더 많은 표본이 배정된다.
  • 기본 정책: min(64, 세그먼트 수)개의 고유 세그먼트를 Fisher-Yates 셔플로 비중복 추출한다. 세그먼트 수가 64 미만이면 전수 검사한다. 8개/20% 초안 정책은 적용하지 않는다.
  • 한 스텝이 여러 공유 포털을 가지면, 서버는 그중 하나를 무작위로 고르지 않고 전 포털을 검사한다. 모호함을 클라이언트에게 맡기지 않는다.
  • 선택된 스텝에서는 포털 선분을 최대 검증 간격 이내로 나눈 여러 내부 점 + 양끝점, 그리고 두 다각형 내부로 이어지는 구간의 점을 검사한다(비볼록·오염된 다각형 방어).
  • 해안선, 협수로, navmesh 경계, 큰 방향 변화는 위험 점수를 높여 추가 표본을 배정한다(별도 과제, 이번은 길이 가중만).
  • 표본 수, 샘플 간격, 허용 폭, 위험 가중치는 서버 설정 및 navmesh 버전에 귀속시켜 감사 로그에 기록한다.
  • 반복 요청에서 표본을 조금씩 바꿔 우회하는 행위를 줄이도록 동일 plan 지문에 대한 검증 결과를 캐시하고 재요청 비용을 제한한다.

신뢰 구간(신뢰 경로 섹션)은 표본으로 추출되며 전체 경로 인접성을 결정론적으로 순회하지 않는다. 표본에 포함되지 않은 세그먼트에는 확률적 갭/재시도 리스크가 존재한다. 실제 표본 수와 간격은 map 해상도, 선박 빔, 업데이트 빈도 및 서버 부하 측정 후 확정한다. 위 값은 시작점이지 안전 보증값이 아니다.

7.1 좌표계 규약 (server global ↔ navmesh) — 확정/미확정 분리

이 절은 서버 권위 좌표와 클라이언트 navmesh 좌표의 관계를 확정된 것과 미확정인 것으로 나눠 기록한다. 검증 로직은 다각형 인덱스만 다루므로 어떤 좌표도 wire 에 실리지 않는다(7장 클라이언트 매핑). 좌표는 서버 navmesh 내부에만 존재한다.

  • 확정 — 서버 글로벌 좌표. NWO_RegionNode/MoveMent.cs의 MoveMent.globalPosition은 nwo_Vector3(Int32 X, Int32 Y, Int32 Z) 기반의 대형 정수 XYZ 좌표다. 실사용 범위/정밀도는 저장소에 정의되어 있지 않다.
  • 확정 — 타일 나누기. 같은 생성자에서 tilePosition = (X/2560, Z/2560), position = (X/2560, Y, Z/2560)로 X/Z 를 정수 2560 으로 나눈다. 즉 서버가 사용하는 타일 좌표 단위는 2560 좌표 단위(tile divisor 2560)이며, 이 2560이 서버 측에서 확정된 유일한 수치다. 2560 의 물리적 의미(미터/센티미터/기타)는 저장소에 명시가 없다.
  • 확정 — EchoServerHandler 잔여 스케일. 같은 핸들러에서 타일 연산 후 좌표에 ×10을 곱해 전달한다(position * 10). 이 10배 스케일이 서버 측 파이프라인에서 확정된 마지막 승수다.
  • 미확정 — 대형 월드 전체의 스케일 크기. 서버 저장소에서 확정된 것은 타일 나누기 수치 2560 과 그 좌표 단위뿐이다. 월드의 총 길이나 전역 축척(world scale)을 이 2560으로부터 환산해 확정하지 않는다. 알려진 것은 2560 좌표 단위까지다.
  • 확정(구조) — 클라이언트 변환 표면. 클라이언트 ShipAI는 GeoNavMapTransform/NavMeshJsonRenderer 를 통해 스케일 적응된 대형 좌표를 렌더링하고, 변환 파라미터 centerPivot, worldScale, invertZ 는 구성 가능(configurable)하게 노출된다. navmesh JSON(format navmesh-merged-convex, 정점 [x, y] with y down, polygons/portals/centroids 포함)이 선언하는 메타데이터는 입력 계약일 뿐 서버-클라이언트 스케일 대응을 증명하지 않는다.
  • 미확정 — 원점·축/부호·스케일 대응. 서버 글로벌 X/Y/Z 와 navmesh 로컬 좌표 사이의 원점(origin), 축 매핑과 부호(invertZ, y-down vs Z-up), 스케일 비율은 서버 저장소 코드에서 확정되어 있지 않다(클라이언트 애셋은 서버 저장소 밖의 별도 체크아웃에 있다). 확정하려면 실제 클라이언트 변환 소스(GeoNavMapTransform/NavMeshJsonRenderer의 실제 centerPivot/worldScale/invertZ 값)와 서버 좌표 소스(MoveMent.globalPosition 및 실제 클라이언트 송신 좌표)를 대조 캘리브레이션해야 한다. 그 전까지는 미해결/구성 가능 항목으로 취급한다.
  • 비권위 가정 금지. navmesh JSON 이나 화면상의 격자/타일 개수로 worldScale 을 역산해 확정하지 않는다. 서버-클라이언트 좌표 대응은 반드시 명시적 구성/캘리브레이션 파라미터로 다뤄야 하며, 저장소 코드가 이를 정의하지 않는 한 특정 수치를 확정하지 않는다.
  • 권위 소스. navmesh.json 은 서버가 다각형/포털 기하를 읽어들이는 소스이며, 서버가 그 기하를 소유한다. 클라이언트는 통과한 다각형 인덱스만 순서대로 보내며 기하를 전송하지 않는다. 클라이언트가 보낸 어떤 수치도 좌표 근거로 사용하지 않는다.

좌표 변환(서버 글로벌 XZ ↔ navmesh 로컬)의 비율·원점·축 부호는 실제 클라이언트 변환(GeoNavMapTransform/NavMeshJsonRenderer)과 서버 좌표 소스(MoveMent.cs)를 기준으로 캘리브레이션해 확정한다. 확정 전까지 IAuthoritativeNavMesh의 Classify/LocatePolygon 에 들어가는 nav 좌표의 절대 스케일은 미해결이며, 검증 로직은 nav 좌표 한계 안에서 상대적으로만 동작한다(비율·스텝 길이·통행 폭 임계값은 navmesh 빌드와 캘리브레이션 확정 후에 확정한다).

9. 보안 및 구현 주의

  • 클라이언트 polygonIndex는 증거가 아니다. 정수 몇 개로는 통행 가능성을 증명할 수 없다. 서버는 자기 navmesh에서 인접성·포털 폭·통행 분류를 다시 계산한다.
  • 인덱스는 navMeshVersion 안에서만 의미를 가진다. 버전 검증을 인덱스 해석보다 먼저 수행하고, 불일치 시 인덱스를 아예 해석하지 않는다.
  • shipId는 본문에서 받지 않는다. 인증된 세션에서 서버가 결정한다. 요청 필드를 권한 증명으로 쓰지 않는다.
  • 검증은 navmesh 버전과 이동 규칙 버전으로 고정해 나중에 같은 결과를 재현한다.
  • 실패 상세 지점이나 비밀 표본 인덱스를 클라이언트에 돌려주면 공격자가 다음 요청을 조정할 수 있으므로 일반 응답에는 decision/reasonCode만 제공한다.
  • 요청 본문은 전부 클라이언트 제어 입력이다. 길이·개수·버전 검증은 할당과 인덱싱 이전에 끝나야 한다.
  • 검증 대기 중 선박 위치가 변할 수 있으므로 sequence 및 서버 위치 시각 기준을 명시하고 만료 계획은 다시 제출하게 한다.
  • 통행 가능성 판정은 경로가 물리적으로 안전하거나 실제 선박 제어기가 그 경로를 따를 수 있음을 뜻하지 않는다. 충돌 회피와 동적 장애물은 별도 계층이다.
